# VeriBrand AI — Evidence-Grounded Product Implementation

**Implementation date:** 2026-11-15
**Repository branch:** master
**Scope:** Product gaps A–G from the ground-up assessment

## Product direction

VeriBrand AI is being shaped as an evidence-grounded brand-governance workspace. Its core workflow is:

1. A creator uploads a source document and supplies a metric key / phrase and source citation.
2. A reviewer downloads and inspects the original file.
3. The reviewer transcribes the exact approved fact/value and its validity dates.
4. The application records the reviewer decision, source metadata and SHA-256 digest.
5. The authoritative server verifier checks matching claims against active, reviewer-approved facts.
6. Mismatches become CONFLICT; facts without approved evidence remain UNVERIFIED.
7. Reviewers can approve only after unresolved claim findings are resolved, or use a documented exception.
8. Admins can add persistent workspace brand rules. Review analytics use persisted findings and appeals.

## Implemented changes

### A. Evidence-to-verifier connection

- Added approved value, valid-from and valid-until fields to evidence records through additive SQLite migrations.
- A document cannot become a trusted fact unless it is an uploaded file with a stored path and checksum.
- Reviewer approval requires a non-empty transcribed fact/value.
- The verifier reads active approved facts from the database, checks that the source file still exists, recomputes SHA-256, and excludes missing or altered files.
- Known demo metric recognizers are downgraded to UNVERIFIED unless a matching reviewer-approved fact exists.
- Custom metric keys can map a phrase in a sentence to a numeric claim; matching values can be VERIFIED and mismatches become CONFLICT.
- This is a human-extracted fact workflow, not automatic PDF parsing, OCR or proof of issuer authenticity.

### B. Evidence access isolation

- Creator list queries are filtered by authenticated uploader ID.
- Creator detail and download requests for another creator's evidence return 404.
- Reviewer/admin access is retained for review.
- Ownership isolation is covered by a two-creator integration test.
- **Scope limitation:** this is a single-workspace permission model. Reviewers/admins can see workspace evidence. Organization/tenant IDs and cross-customer isolation are not implemented, so this must not be described as a multi-tenant SaaS boundary.

### C. Verdict and score semantics

- Live editor preview, submission creation and resubmission use the server-side evidence-aware audit.
- The /api/audit endpoint requires an authenticated session.
- The editor labels the 0–100 value as a configured-rule heuristic, not a compliance certification.
- The editor no longer displays “Ready for Publication” based on a high score.
- Standard reviewer approval is blocked for unresolved claim-verification findings and unresolved critical rule findings.
- A reviewer may still make a documented exception with a rationale.
- “No configured issues detected” means only that the configured checks found no issue; it is not a statement of legal or regulatory compliance.

### D. AI capability representation

- The authoritative workflow uses deterministic TypeScript rules and evidence checks.
- The optional Python service is no longer allowed to supply authoritative verdicts through the Next.js audit endpoint.
- This removes the runtime dual-engine fallback from the core workflow.
- Rewrites remain deterministic templates; no claim is made that they are generated by a context-aware LLM.
- The existing palette checker remains a color-token/contrast utility, not image understanding or multimodal creative inspection.

### E. Reverse Brand Intelligence

- Removed seeded benchmark percentages from the heatmap.
- Added an authenticated reviewer/admin analytics endpoint that aggregates persisted submission findings and appeal decisions.
- The UI shows a no-data state when there is not enough persisted activity.
- Appeal rates are described as descriptive signals, not proof of ambiguity or causation.

### F. Brand Vault configuration

- Added a persistent SQLite table for admin-created workspace rules.
- Added an authenticated Brand Vault API; rule creation is admin-only.
- Added a UI for adding terminology, tone, legal, claim and visual rules.
- Custom rules are applied by the server-side verifier.
- Bundled Inkloom-specific rules are shown as inactive reference templates and are not applied to other workspaces by default.
- Reviewer-approved facts appear in the metrics registry.
- **Scope limitation:** rule creation is implemented; full edit/deactivate/version/approval lifecycle and independent organization workspaces are not yet implemented.

### G. Verifier architecture

- Live editor audits, submission creation and resubmissions now use the evidence-aware TypeScript server runtime.
- The Python verifier is not used to produce authoritative product verdicts.
- The TypeScript engine remains deterministic. Python files are retained as optional diagnostic/reference code and are not a second authority.

## Remaining product and deployment gaps

1. **Multi-tenant organizations:** currently one workspace, not isolated customer organizations. A production SaaS needs organization records, memberships, organization-scoped evidence/rules/submissions/analytics, and tenant-boundary tests.
2. **Automatic source extraction:** PDFs/images are uploaded and reviewed manually; no OCR/PDF parsing pipeline, extraction confidence, page/region citations, or extraction review queue exists.
3. **Source authenticity:** SHA-256 proves stored bytes have not changed since upload. It does not prove who issued the file or whether the source is genuine.
4. **Brand rule lifecycle:** custom rules can be added, but editing, deactivation, versioning, approval states and change impact review remain to be built.
5. **Claim detection coverage:** deterministic recognizers and metric-key matching do not guarantee detection of every factual claim. Unknown claims should remain unverified where detected; undetected claims remain a product risk.
6. **Visual creative inspection:** uploaded images are not analyzed for visual brand compliance. Palette checking still operates on supplied color tokens.
7. **Full WCAG conformance:** not established.
8. **PostgreSQL:** not migrated; SQLite remains the runtime database.
9. **Production monitoring/recovery:** Docker health and local persistence do not establish production monitoring, backup/restore drills, RTO/RPO or incident response.
10. **Independent penetration test:** not performed.
